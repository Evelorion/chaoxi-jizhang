# 03 · 算法：问账本（查询侧）

> "读取方向"的完整算法说明。核心思想：
> **模型只做"自然语言 ↔ 结构化"的翻译，检索与统计全在本地做，模型永远不读账本。**

---

## 1. 为什么不能把账目塞给模型

手机本地模型（0.6B～1.7B）的瓶颈不是"想得慢"，而是**要读的字太多**：

| 做法 | 5 万笔账时模型要读 | 结果 |
| --- | --- | --- |
| 把最近的流水拼进提示词 | 900 字起步，且随账目增长 | 慢、贵、还会算错 |
| **本方案：两步翻译** | **约 300 字（问题 + 一行条件）** | 与账目数量无关 |

而且算术交给自己就不该让模型做 —— 它会算错，还没有审计线索。

---

## 2. 四级决策：先本地规则，再模型，最后如实说没听懂

真机反馈过「答非所问」：那时的顺序是「模型解析 → 失败就把整段流水塞给模型自由发挥」，
0.6B 小模型读一堆流水立刻开始幻觉（"您以后换了个项目了"）。现在改成四级：

```
① 本地规则解析（parseLedgerQuerySpecByRules）
     常见问法一眼看懂：今天/昨天/本周/上周/本月/上个月/今年/最近N天、
     花了多少/几笔/平均/最多/最近一笔/有没有/找/对比/汇总/什么时间、
     分类名、渠道、商户名、金额。命中即本地执行，**不调用模型**。
② 模型翻译（查询条件 JSON）
     规则看不懂时才问模型，输入约 300 字。
③ 本地模糊检索兜底（bigram FTS + 向量）
     模型也没给出合法条件时，本地找最像的几条，再让模型挑一条。
④ 如实说没听懂
     给出示例问法，**绝不把整段流水塞给模型**（那是「答非所问」的根源）。
```

两个附带收益：

- **模型没装 / 跑不动时，常见问题照样能答**（走 ①，直接给算好的数字）；
- 常见问题少了一次「翻译」生成，体感更快。

## 3. 主流程


```
用户问题（打字 / 语音）
   ▼
第一次生成：本地千问只输出一行"查询条件 JSON"（输入约 300 字，零账目）
   ▼
Context Manager：追问时继承 / 替换 / 清空上一轮条件
   ▼
本地执行：
   ├─ 结构化（sum/count/average/compare/top_*/latest/monthly_summary/find）
   │     → 统计缓存优先，命中即 O(1)，未命中退化到一次线性扫描
   └─ 模糊（fuzzy）→ bigram 全文检索 → TF-IDF 向量余弦重排 → Top5
   ▼
第二次生成：把"一行结果"或"5 行候选"交给千问，只说一句中文
   ▼
答案 + 命中的流水卡片（可点击跳转）
```

## 4. 查询 DSL（不让模型写 SQL）

模型输出的固定结构：

```json
{
  "continue_context": false,
  "intent": "sum",
  "merchant": null,
  "category": null,
  "channel": null,
  "start_date": "2026-09-01",
  "end_date": "2026-09-30",
  "limit": null
}
```

### 4.1 十种意图

| intent | 含义 | 本地实现 |
| --- | --- | --- |
| sum | 求和 | 过滤后累加 |
| count | 笔数 | 过滤后计数 |
| average | 平均每笔 | 合计 / 笔数 |
| compare | 与上一期对比 | 算出等长上一期，递归调用 sum |
| top_merchant | 哪个商户花最多 | 按商户分组求和，取前 3 |
| top_category | 哪个分类花最多 | 按分类分组求和，取前 3 |
| latest | 最近一笔 | 时间倒序第一条 |
| monthly_summary | 月度汇总 | 合计 + 分类前 3 |
| find | 找具体几笔 | 时间倒序取前 N（默认 5，上限 15）|
| fuzzy | 说不清商户/分类的模糊找 | 见 $6 |

### 4.2 解析与校验（模型说错也不怕）

```dart
parseLedgerQuerySpec(raw):
  取第一个 { 到最后一个 } → jsonDecode
  intent 必须在白名单里，否则整体判为"解析失败" → 走兜底
  category：中文分类名 → 分类ID（完全匹配 → 名称匹配 → 包含匹配）
  start_date/end_date：yyyy-MM-dd（也接受 / 与 . 分隔、yyyy-MM）
  continue_context：必须为 true 才继承
```

**关键点：模型永远不会生成 SQL 片段**，它只能在这些枚举与日期里选择。

### 4.3 提示词（固定且极短）

```
你是记账查询解析器。把用户这句话转成一行 JSON，不要解释、不要多余文字：
{"continue_context":false,"intent":"sum",...}
intent 只能取：sum 求和｜count 笔数｜average 平均｜compare 和上一期对比｜
  top_merchant 哪个商户花最多｜top_category 哪个分类花最多｜latest 最近一笔｜
  monthly_summary 月度汇总｜find 找具体某几笔｜fuzzy 模糊找
今天是 2026-10-06。日期写成 yyyy-MM-dd。
category 填中文分类名；channel 填 微信/支付宝/银行卡/现金。
用户是在追问上一句时，continue_context 填 true，并且只填这次变化的字段。

用户这句话：<问题原文>
参数：maxTokens 90
```

## 5. Context Manager：追问不串题

规则只有一句：**新条件下为空的字段继承上一轮，填了的覆盖。**

```dart
LedgerQuerySpec mergedWith(LedgerQuerySpec? previous):
    if (!continueContext || previous == null) return this;   // 开新查询
    return LedgerQuerySpec(
      intent:     intent.isEmpty ? previous.intent : intent,
      merchant:   merchant   ?? previous.merchant,
      categoryId: categoryId ?? previous.categoryId,
      channel:    channel    ?? previous.channel,
      startDate:  startDate  ?? previous.startDate,
      endDate:    endDate    ?? previous.endDate,
      limit:      limit      ?? previous.limit,
    );
```

对话示例：

| 用户 | 模型输出 | 合并后 |
| --- | --- | --- |
| 这个月麦当劳花了多少 | sum + merchant=麦当劳 + 本月 | 本月 · 麦当劳 · sum |
| 上个月呢 | continue + 上月 | 上月 · 麦当劳 · sum |
| 星巴克呢 | continue + merchant=星巴克 | 上月 · 星巴克 · sum |
| 今天一共花了多少 | **continue=false** + 今天 | 今天 · 无商户 · sum（不粘着星巴克）|

上一轮条件保存在控制器里（lastQuerySpec），页面退出再进也能接着问；
查不到结果的查询**不会**污染上下文（空结果时不覆盖上一轮）。

## 6. 本地执行与统计缓存

### 6.1 过滤与计算

```dart
runLedgerQuery(book, spec, now, statsIndex):
  只给了 start → end = 该月最后一天；只给了 end → start = 该月第一天
  过滤：分类 / 渠道（来源标签或渠道名包含）/ 商户（去空格与 · 后包含）
  按 intent 分派计算，全部是 Dart 里的纯计算
```

### 6.2 统计缓存（#13/#14）

```dart
buildLedgerStatsIndex(book):
  days['yyyy-MM-dd']  → { expense, income, count, byCategory, categoryCounts }
  months['yyyy-MM']   → 同上
  一次遍历建好；range(start, end) 按天累加

失效方式：版本对比（结构上不可能不一致）
  key = "${book.entries.length}|${book.updatedAt.millisecondsSinceEpoch}"
  key 变了 → 重建；没变 → 直接复用
```

**纯时间/分类的 sum、count、monthly_summary 走缓存**，不扫全表；
带商户或渠道条件的查询仍然精确扫描（缓存里没有这两个维度）。

测试固化了两条不变量：缓存结果 == 扫全表结果；加一笔账后统计立刻跟上。

## 7. 模糊检索：FTS + 本地向量

用于"说不清商户和分类"的问题，例如 **"前几天买手机配件那笔钱是多少"**。

### 7.1 分词：中文 bigram + 短词整词

```dart
ledgerSearchTokens(text):
  清洗（只留数字/字母/汉字）→ 按空格切块
  纯数字块     → 整块保留（金额、日期）
  长度 ≤1      → 整块保留
  其它         → 所有相邻两字 bigram + （长度 ≤4 时）整词
```

"手机配件" → 手机 / 机配 / 配件，因此能命中备注里的"XX数码配件店"。
不引入分词库，安装包不增大。

### 7.2 两条打分

每条流水被索引的文本 = 标题 + 商户 + 对象 + 备注 + 标签 + **分类名** + 渠道 + 资金来源 + 金额。
另外把**分类关键词**也加进向量 —— 于是问"打车"能命中"出行"分类下的流水（一点点语义泛化）。

```
① 全文（lexical）
   命中数 = 查询词与文档词的交集大小
   lexical = 命中数 / (文档词数 + 1)

② 向量（semantic，TF-IDF 稀疏向量 + 余弦）
   tf  = 1 + ln(词频)
   idf = ln((N + 1) / (df + 1)) + 1        N=文档数，df=含该词的文档数
   cos = (A·B) / (|A| · |B|)
```

### 7.3 两段式检索

```
第一段：lexical > 0 的按分数排序，取前 20 条候选（挡住噪声）
第二段：对这 20 条算余弦，重排
        score = lexical × 0.6 + semantic × 0.4 + recency
        recency：7 天内 +0.12，30 天内 +0.06（"前几天那笔"更可能是近的）
输出：Top 5
```

**完全不重叠**的问题（如"恐龙化石"）返回空 → 如实回答"没找到"，不硬凑。

### 7.4 交给模型的只有 5 行

```
1. 2026-10-04 淘宝 · 手机壳 39.00元 商户：数码配件店 备注：淘宝 · XX数码配件店
2. ...
问：前几天买手机配件那笔钱是多少
系统提示：只根据给出的候选挑出用户问的那一笔，用一句中文说清楚；不要编造。
参数：maxTokens 120
```

### 7.5 关于"向量"的说明（不吹牛）

这里是**本地稀疏向量（TF-IDF 余弦）**，**不是神经网络 embedding**。
好处：不额外背一个 embedding 模型也能做词形无关的重排。
局限：跨词语义（"给猫买的东西"→"猫粮"）命中有限。
升级路径已留好：searchLedgerFuzzy 内部就是两段式，换掉第二段即可。

## 8. Token 预算

| 阶段 | 输入 | 输出上限 |
| --- | --- | --- |
| 查询解析 | 系统约 230 字 + 上一轮条件 + 问题 40 字 ≈ **300 字** | 90 |
| 结构化作答 | 系统 50 字 + 问题 40 字 + 结果 60 字 ≈ **150 字** | 120 |
| 模糊作答 | 系统 60 字 + 问题 40 字 + 5 行候选 ≈ **300 字** | 120 |
| 通知字段生成 | 固定规则 + 6 行通知（每行 ≤70 字） ≈ **600~900 字/批** | 300 |
| 通知修复轮 | 序号 + 商家 + 原文短句 ≈ **200 字** | 80 |
| 异常解释 | 一行数字 ≈ **60 字** | 100 |
| 模型自检 | 一行 | 16 |

改造前单次提问 4148 字（含 15 条流水明细）→ 现在约 300 字，**且不随账目增长**。

## 10. 边界与失败处理

| 情况 | 行为 |
| --- | --- |
| 模型没装 / 库加载失败 | 提示去装模型；不影响记账等其它功能 |
| 查询条件解析失败（非法 intent / 不是 JSON）| 退回"本地筛好再问"的兜底路径 |
| 查不到 | 直接如实回答"没有找到符合条件的流水"，**不再多调一次模型** |
| 模糊检索为空 | 回答"没找到，换个说法试试" |
| 追问无上下文 | 按新查询处理（不带上一轮实体） |
