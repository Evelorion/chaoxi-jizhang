# 01 · 架构总览

> 潮汐账本（chaoxi-jizhang）· 本地 AI 自动记账引擎
> 本文说明系统长什么样、数据怎么流、AI 出现在哪里、为什么这样切分。

---

## 1. 一句话定位

这不是"通知来了让 AI 看一眼"的功能，而是一台**跑在手机上的记账引擎**：

> **AI 负责理解语言，程序负责事实、统计和执行；规则负责速度。**

具体来说：

| 谁 | 负责什么 | 绝对不做什么 |
| --- | --- | --- |
| 通知解析（正则） | 金额、币种、收支方向、渠道、时间、卡尾号 | 不猜分类 |
| 本地 AI（千问） | 分类、标题、商户、标签、备注、心情、把问题翻译成查询条件、把结果说成人话 | **不碰金额**、不做算术、不读全账本 |
| 规则 / 缓存 / 模板 | 已经确定过的结论（商户分类、通知骨架），直接复用 | 不覆盖用户手动改过的分类 |
| 数据库（加密账本） | 真相：金额、时间、关联关系、统计 | 不信任模型未经校验的输出 |

---

## 2. 两条主链路

系统只有两条链路，**它们不共用上下文**：

### 链路 A：通知 → 账单（写入方向）

```
Android NotificationListener
        │  （只做三件事：存原文、入队、返回；不阻塞、不调用 AI）
        ▼
RawNotificationStore（原文收件箱 ≤120，仅"看起来像支付"的）
        │
        ▼
AutoCaptureStore（待处理队列 ≤120，持久化，带丢弃计数）
        │
        ▼
快速预处理（包名白名单 + 支付特征词 + 正则提取金额/收支/卡尾号）
        │
        ▼
    ┌── 模板快路径（同类通知见过 ≥3 次）→ 直接复用结论
    ├── 商户缓存（这个商户判断过）      → 直接复用结论
    └── 本地千问（新商户/新格式）      → 生成完整字段
        │
        ▼
校验（分类合法性 / 反编造 / 置信度阈值）→ 失败则「抢救 → 修复轮 → 待确认」
        │
        ▼
关联打分 → 多条通知合并成一笔（≥90 分才自动合并）
        │
        ▼
冲突解析（字段级优先级）→ 退款绑定 → 写入加密账本
        │
        ▼
学习：商户缓存 / 通知模板 / 延迟画像 / 通知顺序 / 路径统计
```

### 链路 B：提问 → 答案（读取方向）

```
用户问题（打字或语音）
        ▼
本地千问：只输出一行"查询条件 JSON"（输入约 300 字，**完全不含账目**）
        ▼
Context Manager（追问时继承上一轮条件：换实体 / 换时间 / 开新查询）
        ▼
    ┌── 结构化问题 → 本地精确计算（统计缓存优先，几毫秒）
    └── 模糊问题 → bigram 全文检索 → TF-IDF 向量余弦重排 → Top5
        ▼
把结果（一行数字 或 5 行候选）交给千问
        ▼
千问只说一句话（输入约 150 字）
```

## 3. 三条速度路径（越用越快的原因）

| 路径 | 触发条件 | 是否调用模型 | 大致耗时 |
| --- | --- | --- | --- |
| **① 模板快路径** | 通知骨架已见过 ≥3 次且没被用户改过 | ❌ 不调用 | <100ms |
| **② 商户缓存** | 这个商户千问判断过一次 | ❌ 不调用 | <100ms |
| **③ 千问** | 新商户 / 新通知格式 | ✅ 调用 | 1～3s（批量 6 条一次） |

优先级：**商户缓存 > 模板 > 千问**。这样你手动改过的分类永远压过模板，不会"学歪"。

界面上能直接看到占比（设置页「自动记账处理情况」）：

```
已处理 40 条：不用模型 72%（模板 12 · 商户缓存 17 · 千问 11）
```

目标状态是：新用户 AI 参与 ~70%，用一个月后降到 ~25%。

## 4. 完整决策树（收到一条通知之后）

```
收到通知
  │
  ├─ 是支付类通知吗？（包名白名单 + 特征词）
  │     否 → 原文都不存，直接丢弃
  │     是 ↓
  ├─ 用户关掉了这个来源的开关？ → 是：确认出队，不入账
  │
  ├─ 有可信模板？ ── 有 → 用模板结论
  ├─ 商户在缓存里？ ─ 在 → 用缓存结论
  │     都不在 ↓
  ├─ 本地千问生成字段（一批最多 6 条）
  │     ├─ 严格 JSON 解析成功 → 用
  │     ├─ 失败 → 文本抢救（按"序号…分类ID"位置关系捞）
  │     ├─ 仍失败 → 修复轮（只重问失败的那几条，maxTokens 80）
  │     └─ 仍失败 → 标「待确认」照常落账（**绝不丢通知**）
  │
  ├─ 已有同一笔的账单？ → 关联打分
  │     ≥90 → 自动合并；多个同强候选 → 不合并（宁可两条）
  │
  ├─ 字段冲突？ → 按字段优先级取值（金额信银行、商户信电商、分类信用户）
  │
  ├─ 校验（负数金额纠正、分类合法、反编造）
  │
  ├─ 写入加密账本 + 更新统计缓存
  │
  └─ 队列还有货？ → 前台服务保住进程，30 秒后再来一轮
```

## 6. 八条不可动摇的设计原则

1. **通知先落盘、再排队、最后才谈 AI** —— 监听线程永不做重活，App 被杀也不丢通知。
2. **金额只能来自通知解析** —— 模型输出里根本没有金额字段，从接口上杜绝模型编金额。
3. **AI 不读账本** —— 提问时模型只看"问题 + 一行查询条件"，回答时只看"一行结果"。
4. **没有 AI 也要能用** —— 模型没装/跑不起来时，通知留在队列等待，其余功能完全不受影响。
5. **解析失败不丢数据** —— 四道防线，最后一档是"按待确认落账"。
6. **宁可不合并，不要错合并** —— 两笔真实消费被并成一笔，比多出一条更难发现。
7. **用户改过的永远最大** —— 用户修正写入商户缓存，压过模板与模型。
8. **动画一次性、只做 transform/opacity** —— 循环动画是卡顿与耗电的头号来源，禁止。
