# 05 · 本地模型与性能

> 这一节回答两个问题：**模型怎么装、怎么跑得动**，以及**为什么它不卡、不烫、不费电**。

---

## 1. 模型清单

| 编号 | 名称 | 大小 | 适用 |
| --- | --- | --- | --- |
| qwen3-06b-q4 | 千问轻量版 | 429 MB | 占用小，推荐先装这个 |
| qwen3-06b-q8 | 千问清晰版 | 805 MB | 回答更稳，占用稍大 |
| qwen3-17b-q4 | 千问标准版 | 1.28 GB | 分析更细，需要内存大一些 |

每个模型都带 **SHA-256 与精确字节数**，下载完成必须两个都对上才算装好：

```
qwen3-06b-q4  da2572f1…6417d4  428,970,080 字节
qwen3-06b-q8  361cc681…9e1d    804,753,632 字节
qwen3-17b-q4  d2387ca2…b7b5    1,282,439,264 字节
```

### 1.1 下载（Android DownloadManager）

```
最多 3 次尝试，退避 5s / 20s / 60s
失败后自动改用镜像源（huggingface.co → hf-mirror.com）
断点续传由 DownloadManager 负责
完成后：核对字节数 → 核对 SHA-256 → 写 .verified 标记
```

一个踩过的坑：DownloadManager 会**预分配**目标文件，所以"文件大小 = 总大小"不代表传完，
早期版本因此在传输中途就去校验，导致"校验失败 → 删除 → 重下"的死循环。
现在只有 `已接收 >= 总大小` 或状态为成功时才允许校验。

### 1.2 能不能跑：先看 ABI，再加载库

```dart
localAiInferenceSupported = Abi.current() in { androidArm64, androidX64 }
```

手机端推理库是 64 位 ARM（arm64-v8a）。所以：

| 设备 | 结果 |
| --- | --- |
| 一加 15 等 arm64 手机 | ✅ 正常推理 |
| x86_64 模拟器 | 模型能下载，但 `libllama_jni.so` 加载不了（**设备限制，不是 App 不支持**） |
| 32 位 ARM 老机 | ❌ 同上 |

自检（设置 → 离线千问 → AI 自检）会把**处理器类型、推理库、模型文件、试跑一次**四项分别列出来，
并把结论说成人话；界面上"能不能用"的判断来自"**真的加载一次库**"，不是猜。

> 曾经的真机 BUG：所有手机（含 arm64）都显示"不支持"。
> 原因是 `canRunLocalAi` 被写在取 `modelId` 之后，参数缺失先抛异常，
> Dart 侧把通道错误当成"设备不支持"。现在自检放在取参数之前，并且区分"明确不支持"与"通道异常"。

## 2. 引擎生命周期：热着用，别反复加载

真正拖慢体验的往往不是生成速度，而是**模型加载**（几百 MB 读盘 + 初始化）。

```
LocalAiEngine.acquire(modelPath)
  ├─ 已有同路径的常驻实例 → 直接复用（并重置 5 分钟空闲计时）
  └─ 不同模型 → 释放旧的，加载新的

空闲 5 分钟 → 自动释放内存
生成期间 → 空闲计时不生效（不会被中途释放）
聊天页退出 → 故意不释放（保持"热"）
```

启动预热：进入问账本页面时就后台预热一次，等用户真的打字时首 token 更快。

## 3. 两级模型：记账用小的，问答用大的

```dart
_captureModelFor(settings):
    在**已安装**的模型里挑 byteSize 最小的那个
    没有已安装的 → 用设置里选中的（后续会提示去装）
```

- 通知解析（分类、字段生成）用最小模型：够用、快、省电；
- 问答 / 分析 / 模糊找用用户在设置里选的模型。

你装了大模型也不会拖慢记账，也不用多一个设置项。

## 4. 推理参数与预算

| 参数 | 值 | 理由 |
| --- | --- | --- |
| contextSize | 4096 | 提示词已压到几百字，4096 足够且更省内存 |
| 线程数 | min(6, 核心数-2)，≤4 核时取核心数-1 | 留出核心给界面，避免抢 CPU 反而更慢 |
| 通知字段生成 | maxTokens 300, temperature 0.1 | 固定 JSON |
| 修复轮 | maxTokens 80, temperature 0 | 只要一个分类 |
| 查询解析 | maxTokens 90 | 一行 JSON |
| 作答 | maxTokens 120 | 一句话 |
| 自检 | maxTokens 16 | 一行 |
| 批大小 | 6 条通知 | 批间 clearContext |

**输出必须短**：小模型一旦开始"解释"，不但慢，还会污染 JSON。

## 5. 实测性能（模拟器 + 真机反馈）

| 项目 | 改造前 | 改造后 |
| --- | --- | --- |
| 首页空闲帧（10 秒） | 603 帧 | **140 帧** |
| 首页空闲 CPU | 46~50% | **0%** |
| 洞察页滚动卡顿率 | 1.14% | **0.23%** |
| 单次提问模型输入 | 4148 字（含 15 条流水） | **约 300 字（零账目）** |
| 提问时模型要读的账目 | 15 条明细 | **0 条** |

卡顿的根因是**循环动画**：语音悬浮球的阴影用 `repeat()` 一直在跑，
即使没人碰它也在每帧重绘。现在的铁律：

> **动画必须一次性，只做 transform / opacity，禁止循环。**

其它措施：每张卡加 `RepaintBoundary`（阴影模糊很贵）、
`IndexedStack` 的页面 memo 缓存、
离开屏幕的页面用 `TickerMode` 停掉轮询、状态没变不写 state。

## 6. 后台常驻服务

```kotlin
CaptureDrainService（前台服务，foregroundServiceType=dataSync）
  启动：队列里还有待处理通知（由 Dart 侧 startCaptureDrain 调用）
  通知：低优先级、常驻，"潮汐账本正在整理账单 / 还有 N 条通知等着生成账单"
  停止：队列清空时自动 stopService
```

Dart 侧配套：只要队列非空，就每 30 秒跑一轮 `syncAutoCapturedEntries(silent: true)`
（锁屏或正在同步时跳过）。

**边界**：
- 它保住的是"App 进程还活着"，所以切后台、锁屏后队列会继续被消化；
- 推理仍跑在 Flutter 进程里，不是独立原生 AI 服务；
- 用户"强制停止"后不会自动复活，下次打开继续处理队列（队列是持久化的）。

## 7. 电量与温度（现状与设计倾向）

现状：队列处理是**事件驱动 + 30 秒轮询**，队列空时完全不做任何事（服务也会停）。
设计倾向（尚未实现）：

```
充电中 + 温度正常 + 电量 > 30%  → 允许批量高速处理历史积压
普通状态                        → 每次最多处理一批（6 条）
高温 / 低电量                   → 只处理实时通知，历史积压延后
实时支付通知                    → 永远最高优先级，可插队
```

## 8. 隐私与安全

| 项目 | 做法 |
| --- | --- |
| 账本 | AES-GCM 加密后落盘，密钥由用户口令派生 |
| 通知原文 | 只存"看起来像支付"的，且只在应用私有目录 |
| 模型推理 | 100% 本地，**不联网** |
| 对话记忆 | 存在加密账本里 |
| 打码模式 | 金额默认打码，开启时金额滚动动画也会关闭（避免用动画"漏"出金额）|
